# 运营部

运营的唯一事实源是 `operations/` 下的规划文件：

- `cold-start-plan.md`：起号阶段总规划（现状盘点、阶段任务、平台配比、纪律红线、复盘记录）
- `ai-tools-series-plan.md`：AI 工具系列排期（及后续新增的系列规划文件）
- `publish-log.md`：发布台账，逐篇发布记录 + 24h 数据——配比检查和周复盘的数据源

**边界说明**：系列规划（排期、节奏、平台分工、数据检查点）属运营部，放 `operations/`；但排期表里的每一期只是选题预备队——真正启动时仍走选题部流程在 `ideas/` 沉淀成选题文件。

本 skill 不写稿也不审稿，只回答两个问题：**这个选题现在该不该做？账号现在跑得怎么样？**

## 职责一：选题评估（选题环节强制调用）

输入：一个选题（想法描述或 `ideas/` 下的选题文件）。对照规划文件逐项检查：

1. **阶段匹配**：当前处于冷启动哪个阶段、该阶段的核心任务是什么（读 cold-start-plan 的现状盘点和阶段章节）？这个选题服务于这个任务吗？
2. **配比检查**：对照小红书选题配比（70% 可搜索干货 / 20% 热点评 / 10% 观点认知），本选题落在哪一类；查 `publish-log.md` 最近发布记录和 `ideas/` 在产选题，该类额度还够不够。
3. **系列排期**：与进行中的系列（如 AI 工具系列）相关的，查是否与排期重复或冲突；不相关的，评估会不会挤占系列节奏。**快速通道**：选题本身出自系列排期表的，第 1-3 项视为规划时已定，只需确认排期未变，评估重点放在第 4 项平台风险预判。
4. **平台风险预判**：不做完整合规扫描（那是审稿部的事），只做选题级预判——涉加密/web3 的选题小红书版降敏后还成不成立、教程类是否触系列红线（如 Claude Code 获取途径）。预判某平台大概率 ⛔ 的，直接建议该平台跳过。
5. **精力配比**：对照三平台精力分配（当前小红书 ~50% / X ~35% / 公众号 ~15%），本选题的主战场是哪个平台、值不值得三平台全做。

输出三档判定 + 理由：

- ✅ **推进**：符合当前运营需求。附建议：主攻平台、发布时机、配比归类。
- 🔄 **调整后推进**：选题可用但角度/平台/时机需要调整，给出具体调整方案。
- ⛔ **暂缓**：与当前阶段任务不符或风险过高，说明什么条件下可以重启（如"探针测试通过后""系列收官后"）。

**判定只是建议，拍板权在用户**——评估结果交回选题环节，由用户决定推进、调整还是重新提议。

## 职责二：周复盘与规划维护

- **每周日复盘**：按 cold-start-plan「每周复盘」节拉数据填表，回答三个问题（哪篇最好/最差、为什么、下周改什么），结论追加到该文件「复盘记录」节。
- **数据登记**：每篇发布当天在 `publish-log.md` 登记（日期/平台/slug/配比类别），24 小时数据用户提供后回填数据列；周复盘从台账汇总进 cold-start-plan「复盘记录」。
- **规划修订**：复盘结论或重大事件（限流/爆款/探针结果）需要改规划时，直接修订 `operations/` 对应文件，注明日期。
- **红线沉淀**：实际运营踩到的新坑（限流原因、违规通知），除更新规划外，同步提醒把新红线写进 `content-review` 对应平台一节（审稿部的知识库）。
